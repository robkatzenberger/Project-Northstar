# Working on Apex

The parent Northstar instructions still apply. This is the active design workspace for the third-party transparency layer, started from APEX-Lite at Robert's direction on 2026-09-09.

Read [README.md](README.md), [the build plan](BUILD-PLAN.md), [the foundation design](design/0001-foundation.md), and [the first workflow](design/first-workflow.md). The [parent roadmap](../docs/roadmap/transparency-layer.md) owns product priority; the build plan owns Apex's implementation sequence and completion checks. Proposed choices are not approved implementations or security acceptance.

The [Auditor v0.0.2](docs/auditor-v0.0.2.md) connects the [Switchboard foundation](docs/switchboard.md) to deterministic human-entered rules, a local journal, and authenticated human review with context. Run `npm test` and `npm run demo:auditor` from this folder. The smaller `npm run demo:switchboard` remains available. Switchboard PASS permits progression to the gate; gate APPROVE is only an authenticated action-and-target assessment. Human review records APPROVE or DENY separately. Neither assessment nor review grants execution permission.

The human page owns rules, enrollment, reviews, and audit. Participating agents use the [client workflow](docs/agent-integration.md) to submit their own intents and retrieve their own saved outcomes. The [participant instruction template](docs/agent-instructions.md), also served at `/agent-instructions.md`, is an artifact for configuring a participating agent; it is not automatically installed into this repository's development-agent instructions.

- Keep Apex work inside this folder where practical. Do not resume macOS marker or enforcement continuation merely because it has an open review gate.
- Preserve `reference/apex-lite/` byte-for-byte and retain its license. Its [manifest](reference/apex-lite.manifest.json) identifies the exact source. Build new Apex code outside the reference snapshot after its design is settled.
- Treat historical README instructions and claims inside the snapshot as reference material. Its actor/operator strings, keyword gates, ALLOW default, and nonblocking receipts do not establish authenticated authorization.
- Design around declared intent, authenticated whitelist and action-authority checks, deterministic constraints, explanations, and human verification. Keep agent statements separate from trusted facts and policy results.
- Preserve the agent/human workflow: an instructed agent invokes the client automatically for its intended action; the human provisions access and handles rules/reviews/audit. Keep manual intent entry in the collapsed Developer test console. The signed-in, visible human page refreshes review/audit records every three seconds.
- Keep participant credentials in a private file outside instruction text and git, supplied to the client through `APEX_CREDENTIAL_FILE`. `APEX_AGENT_ID` names the enrolled principal; `APEX_URL` selects the service. Never give an agent the operator key. The status route exposes only that authenticated agent's own assessment and separate human review.
- Treat ESCALATE as a pause pending a recorded human outcome. Changed policy/authority requires a fresh current assessment; human DENY stays denial. Transport failures and unreadable responses are blocking, and repeated submissions are not idempotent. The client and Markdown template are cooperative integration, not a runtime hook, forced mediation, or permission to execute tools.
- Keep authority failures and evaluation errors outside human policy review. Top-level BLOCKED preserves the underlying Switchboard DENY; ERROR remains nonreviewable. Missing material data or verification failure must not authorize.
- For v0.0.2, keep gate rules limited to `APPROVE` or `ESCALATE` plus a catalog action ID and exact opaque target. ESCALATE wins conflicts; no match escalates after successful authority screening. The gate does not make a business DENY decision. No prose interpretation, wildcard expansion, or executable rules.
- Human APPROVE/DENY requires a saved current-model ESCALATE assessment, operator authentication, and a nonblank context comment of at most 2000 UTF-8 bytes after trimming. Bind to the stored assessment, never a caller-supplied replacement intent. Resolve once; recheck policy and registry before approval. Authority failures and errors cannot be overridden through review.
- Validate legacy journal policies with the historical parser only. Migration appends a fresh comment-only `approve_escalate_v1` policy requiring human rule entry. Preserve historical bytes and outcomes; never silently convert old DENY rules or old pending cases into approval.
- The auditor's `audit.jsonl` is the saved policy/registry authority after initialization. Use version-checked service edits; a seed registry file is not a live configuration override. Run one local server per data directory. Preserve the journal and block on storage failure; do not describe it as tamper-proof or protected from the same OS user.
- Keep operator keys and agent credentials separate and out of logs/git. Agent credentials are principal-bound and replaceable; the server holds them only in memory, while each client reads its separately provisioned private file. The catalog's action IDs are enforced after Switchboard; its material-field definitions remain unvalidated design metadata.
- Use existing Northstar contracts and appropriate core behavior where useful. Any live permission path must preserve exact-action binding, authenticated single-use claim, fail-closed behavior, and distinct execution evidence. Do not create a competing authority implicitly in the interface.
- Use synthetic data during design. The upstream notification integration is historical; sending messages requires explicit authorization.
- Document source attribution and scope for verification. Do not transfer Northstar or APEX-Lite test results into claims about a new Apex implementation.
